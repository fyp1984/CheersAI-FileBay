# CheersAI 企业 AI 知识库平台技术实现方案 V1.0 技术评审报告

> 评审对象：《CheersAI 企业 AI 知识库平台技术实现方案 V1.0》
> 评审日期：2026-07-16
> 评审角色：资深技术架构师 / 项目负责人
> 评审结论：方向基本正确，但不能直接进入真实数据生产建设；必须先完成 M0 安全基线、容量 PoC、RAGFlow/Dify 契约验证和知识控制模块边界固化。

---

## 1. 执行摘要

该方案的总体技术路线是可行的：以 FileBay/Gitea 承载脱敏知识文件和物理版本，以知识控制模块承载业务版本、生命周期、审批、权限、任务和审计，以 RAGFlow 作为可重建的解析与索引引擎，以 Dify 作为应用编排和问答入口。这种分层避免了把 RAGFlow 或 Dify 错误地当作企业知识主库，也避免了首期重新建设一套完整 DMS。

但方案的关键风险也很集中：

1. FileBay/Gitea 适合作为“受控、版本化、低到中等规模知识文件底座”，不适合作为无限扩展的企业网盘或强合规文档销毁系统。
2. 知识控制模块放在 Desktop API 内部，MVP 可以降低交付成本，但长期会形成高耦合、扩容受限和安全边界混杂的问题。
3. RAGFlow 与 Dify 的集成不能只理解为“API 调通”。真正难点在于权限不放大、索引与发布状态一致、下架即时阻断、凭据托管、元数据泄露控制、任务幂等和对账。

本方案有较强的架构意识，已经识别了 TLS、Token、个人仓库与企业知识空间隔离、Git 历史难销毁、Dify/RAGFlow 不作为权威系统等关键问题。主要不足是：成本模型偏隐含，MVP 边界仍偏大，安全基线与容量基线虽然列出但没有成为“不可绕过的投产门禁”，对 RAGFlow/Dify 的版本和接口不稳定性需要进一步合同化。

### 2.2 额外查证

除阅读方案原文外，本评审补充查证了以下接口事实：

- RAGFlow 官方 HTTP API 文档已提供 REST API 参考，并明确 API 认证需要 RAGFlow API Key；同时文档存在 deprecated API aliases，说明版本升级存在接口替换和兼容层风险。
- Dify External Knowledge API 的官方文档说明：Dify 调用外部知识源时会向配置 endpoint 自动追加 `/retrieval`，并以 Bearer Token 形式传递 API Key；Dify 只负责调用外部检索，不负责管理外部内容。
- Dify 文档还指出，External Knowledge API / External Knowledge ID 创建后不可直接修改；Dify Knowledge API Key 覆盖范围较宽，需要谨慎保护。

## 3. 技术可行性与架构风险

### 3.1 基于 Gitea/FileBay 改造为知识库底座是否合理

#### 结论

合理，但边界必须收窄：FileBay 适合作为“脱敏知识文件的版本化权威存储”和“企业知识空间的基础权限容器”，不适合作为完整 DMS、企业网盘、全文搜索引擎、强销毁合规系统或知识生命周期唯一实现层。

#### 合理性

方案复用 FileBay/Gitea 的以下能力是正确的：

| 能力 | 对知识库的价值 |
|---|---|
| 私有仓库 / Organization / Team | 可映射租户、知识空间、管理组 |
| Git commit SHA | 提供不可变物理修订证据 |
| Git LFS | 支撑较大二进制文件 |
| Contents / Raw API | 能复用现有 Desktop 文件链路 |
| Webhook / API | 可作为后续变更通知与对账辅助 |
| 上游 Gitea 生态 | 降低首期基础设施成本 |

方案提出“双版本模型”是一个重要优点：物理版本由 FileBay/Git 负责，业务版本由知识控制模块负责。这避免了把路径、分支或 commit 直接误用为业务生命周期状态。

#### 主要风险

| 风险 | 严重性 | 说明 |
|---|---:|---|
| Git 仓库膨胀 | 高 | 大量 Office/PDF、频繁更新、LFS 对象增长会导致仓库维护、备份、GC 和迁移成本上升。 |
| 大目录与海量文件性能 | 高 | 10 万级文件目录、批量上传、Raw API 并发读取、LFS 指针解析都需要实测，不能凭 Gitea 原生能力推断。 |
| 物理销毁困难 | 高 | Git 历史和 LFS 对象天然不适合“立即不可恢复销毁”。方案已识别该问题，但 M1 必须在产品层明确“下架”和“物理销毁”的差异。 |
| 权限模型错配 | 中高 | Gitea 仓库/团队权限粒度粗于企业知识权限。部门、岗位、项目、密级、有效期、引用权限不能只靠仓库权限。 |
| 上游升级冲突 | 中 | 若后续为知识库深度修改 Gitea 核心，升级成本会快速上升。方案选择“知识控制模块外置”是正确方向。 |

#### 判断

FileBay 可以作为 MVP 的知识文件底座，但必须设置明确容量红线：

- 单文件大小上限；
- 单仓库文件数上限；
- 单租户仓库数量上限；
- LFS 对象容量上限；
- 每日新增文件和更新频率；
- 备份恢复 RTO/RPO；
- 仓库 GC、LFS prune、迁移策略。

若客户需求包括强文控、复杂流程、电子签章、严格留痕、保全、细粒度销毁，FileBay 只能作为文件底座之一，不能替代专业 EDMS。

### 3.2 知识控制模块作为 Desktop API 一部分的利弊

#### MVP 阶段优点

| 优点 | 评估 |
|---|---|
| 复用现有认证、租户、数据库、部署链路 | 能显著降低 M1 交付成本。 |
| 复用 Desktop 与 FileBay 已有文件接口 | 有利于快速形成端到端闭环。 |
| 减少服务发现、网关、队列、独立运维 | 对预算有限团队是现实选择。 |
| 便于快速迭代前端和 Dify 集成 | 产品验证速度更快。 |

#### MVP 阶段风险

| 风险 | 说明 |
|---|---|
| Desktop API 职责膨胀 | 文件、知识治理、RAG 任务、检索、审计混在同一服务，后续边界会变模糊。 |
| 安全边界混杂 | Desktop API 同时面对用户前端、Dify、FileBay、RAGFlow、管理员操作，凭据隔离难度上升。 |
| 扩容模型不清 | 上传、解析任务、检索 API、后台对账的资源曲线不同，不适合长期绑在同一进程。 |
| 故障域扩大 | RAGFlow 任务堆积或检索超时可能拖垮 Desktop API 的其他业务。 |

#### 长期问题

长期看，知识控制模块应逐步演进为独立 Knowledge Control Service。触发条件不应只看“多个调用方”，还应包括：

- 检索流量影响 Desktop API 延迟；
- 后台 Worker 积压影响在线 API；
- 多租户独立部署或专有网络要求；
- 需要独立安全审计、密钥、访问控制；
- 知识功能需要独立版本发布；
- RAGFlow/Dify 之外出现第二个检索或智能体编排引擎。

#### 建议

M1 可以内置在 Desktop API，但必须从第一天按“可拆服务”编码：

1. 独立数据库 schema 或表前缀；
2. 独立配置段和密钥命名空间；
3. 独立服务层、Adapter 层、Worker 层；
4. 不复用现有 `filebay_files.py` 堆业务逻辑；
5. 所有外部调用通过接口抽象；
6. trace_id、tenant_id、actor_id、idempotency_key 全链路传递；
7. 禁止前端直接拿 RAGFlow、FileBay 管理凭据。

### 3.3 RAGFlow 集成隐患

方案将 RAGFlow 定位为“可重建派生数据”，这是正确的。RAGFlow 不应成为企业知识权威系统。

#### 主要隐患

| 隐患 | 严重性 | 说明 |
|---|---:|---|
| API 版本漂移 | 高 | RAGFlow 官方 HTTP API 存在 deprecated aliases，说明不同版本间 API 路径和语义会变化。必须固定版本并做契约测试。 |
| 元数据不是权限系统 | 高 | RAGFlow 文档 metadata 可用于过滤和引用，但不能替代 FileBay/知识控制模块的权限判定。 |
| 数据集隔离不足以覆盖全部权限 | 高 | MVP 按租户、业务域、K等级拆数据集是合理的，但部门、岗位、项目、白名单仍需检索前授权和返回后二次复核。 |
| 删除不等于立即不可检索 | 高 | RAGFlow 删除、索引刷新、缓存清除可能存在延迟。下架必须先在知识控制模块阻断。 |
| 解析质量不可控 | 中高 | PDF、扫描件、复杂表格、图片、页眉页脚、附件、宏文档的解析效果需要样本评测。 |
| 任务幂等和重复上传 | 中高 | 发布重试必须复用相同 idempotency_key，避免一个版本对应多个 RAG 文档。 |
| 原文下载接口风险 | 中 | 方案列出 `download original` 用于核验，但需要严格限定为内部完整性检查，不能暴露给 Dify 或普通用户。 |

#### 建议

1. 将 RAGFlow Adapter 固定到具体版本，例如 `ragflow-vX.Y.Z-profile-N`。
2. 建立 Adapter 契约测试，覆盖 upload、metadata、parse、status、retrieve、delete、timeout、重复请求、异常响应。
3. RAGFlow 文档 ID 与 `knowledge_version_id` 建立唯一约束。
4. RAGFlow metadata 只存低敏治理标识，不存用户、部门明细、密钥、原始路径或敏感分类解释文本。
5. 下架流程必须是“知识控制模块先阻断检索，再异步删除 RAGFlow 派生数据”。
6. 定义解析质量验收集，包括复杂 PDF、扫描件、表格、页码引用和中文标题层级。

### 3.4 Dify 集成隐患

方案选择通过 CheersAI 知识检索 API 被 Dify 调用，而不是让 Dify 直接管理企业知识主库，这个方向是正确的。Dify 官方 External Knowledge API 也是要求外部服务提供 `/retrieval` 检索接口，Dify 调用外部服务并使用返回 chunks 作为上下文。

#### 主要隐患

| 隐患 | 严重性 | 说明 |
|---|---:|---|
| Dify 只做检索调用，不做外部知识管理 | 中 | 这与方案一致，但意味着发布、下架、权限、审计全部要由 CheersAI 自己实现，不能指望 Dify 补齐。 |
| External Knowledge ID 创建后不可修改 | 中 | 数据集迁移、租户拆分、环境切换需要预留重建和映射策略。 |
| Bearer API Key 暴露风险 | 高 | Dify 会把配置的 API Key 作为 Bearer Token 传给外部服务。该 Key 必须是服务端间短期或可轮换凭据。 |
| Dify Knowledge API Key 范围较宽 | 中高 | 如果改用 Dify 内置知识 API，知识库 API Key 可能覆盖创建该 Key 的账号可见知识库，必须避免前端或客户端持有。 |
| 应用绑定数据集可能扩大权限 | 高 | 一个 Dify 应用绑定过大的外部知识源，可能导致越权召回；必须由 CheersAI 检索 API 以用户身份实时裁剪。 |
| 提示词和工具调用边界 | 中高 | Dify 工作流、Agent 工具和检索上下文必须隔离，不能让文档内容提升为系统指令。 |

#### 建议

1. Dify 只接入 CheersAI Knowledge Retrieval API，不直接接 RAGFlow 数据集。
2. Dify API Key、External Knowledge API Key 进入服务端密钥系统，支持轮换、撤销、分环境隔离。
3. 每个 Dify 应用登记允许的 `tenant_id / space_id / K等级 / R等级 / 场景`。
4. Retrieval API 必须强制使用当前用户身份计算权限，不能只信任 Dify 传入的 knowledge_id。
5. Dify 返回给 LLM 的 chunks 必须携带引用 ID，但不应携带内部敏感治理字段。

## 4. 成本与预算评估

### 4.1 显性成本

| 成本项 | 内容 |
|---|---|
| 开发人力 | 知识模型、API、状态机、FileBay Adapter、RAGFlow Adapter、Dify 检索 API、前端、任务中心、审计、测试。 |
| 基础设施 | FileBay 服务、数据库、Git/LFS 存储、Desktop API、RAGFlow、Dify、向量/全文索引相关存储、备份系统。 |
| 安全治理 | TLS 整改、密钥系统、凭据轮换、日志脱敏、病毒/宏检测、提示注入防护。 |
| 测试验证 | 契约测试、集成测试、性能测试、恢复测试、安全测试、代表性文档解析评测。 |
| 运维监控 | 指标、告警、对账、任务重试、容量巡检、备份恢复演练。 |

### 4.2 隐性成本

| 隐性成本 | 风险说明 |
|---|---|
| Git/LFS 长期存储膨胀 | 文件版本、LFS 对象、备份副本、测试环境复制都会增长。 |
| RAGFlow 解析与索引资源 | OCR、复杂 PDF、表格解析、embedding、rerank、索引存储会带来 CPU/GPU/内存/磁盘压力。 |
| Dify 应用治理 | 多应用、多知识源、多 API Key、多环境同步，需要配置治理与审计。 |
| 数据清洗与标注 | 企业知识库最大成本往往不是代码，而是来源梳理、责任人、分类、有效期、权限和质量验收。 |
| 权限对账 | SSO、FileBay Team、知识控制表、Dify 应用授权、RAGFlow 数据集之间需要持续对齐。 |
| 销毁与合规 | Git/LFS 物理销毁、备份到期删除、删除回执和合规证明成本高。 |
| 升级兼容 | Gitea、RAGFlow、Dify 任一组件升级都需要版本组合验证。 |
| 运维人力 | RAGFlow/Dify/FileBay/数据库/备份/监控至少需要兼职 DevOps；规模上来后需要专职。 |

### 4.3 预算有限情况下是否可持续

#### 可持续条件

在预算有限情况下，该方案可以持续，但必须满足以下条件：

1. M0 必须先做安全整改，不进入真实数据；
2. M1 只做人工数据源、单级审批、基础权限、基础 RAGFlow 解析、基础 Dify 检索；
3. 不承诺强文控、复杂会签、文件级 ACL、自动连接器、完整物理销毁和 HA；
4. 容量 PoC 冻结明确上限；
5. 只开放一个内部场景试点；
6. 不为每个客户临时改数据模型和流程；
7. 建立清晰的“超出 MVP 即进入 M2/TCO 评估”规则。

#### 不可持续情形

若 M1 同时要求以下能力，则预算不可控：

- 多数据源自动采集；
- 强合规物理销毁；
- 复杂多级审批；
- 文件级/分块级权限；
- 大规模 OCR；
- 高可用和灾备；
- 多租户计量计费；
- 多 RAG 引擎兼容；
- 与多个企业系统双向同步。

## 5. 逻辑与流程漏洞

### 5.1 导入与登记流程

方案流程基本成立，但存在一个关键边界需要补强：文件导入必须明确区分“本地原件、本地脱敏 Sandbox、远端脱敏包、FileBay 正式知识仓库”。

当前“Desktop 上传或从 FileBay 选择文件”容易产生歧义：

- 如果 Desktop 上传的是原件，则违反本地优先隐私约束；
- 如果 FileBay 个人仓库中已有未脱敏文件，不能直接登记为企业知识；
- 如果服务端执行“再次脱敏”，仍然意味着服务端接触过原件，不可接受；
- 如果导入记录只存路径而不存 SHA-256、脱敏策略版本、授权证据，则后续无法审计。

#### 建议补充硬约束

导入 API 只接受“可提交脱敏包”：

- `masked=true`；
- `mask_policy_version`；
- `mask_manifest_hash`；
- `content_sha256`；
- `source_authorization_id`；
- 禁止上传本地路径；
- 禁止服务端读取用户本地路径；
- 禁止服务端接收未脱敏原件。

### 5.2 审核发布流程

流程设计整体闭环较好，尤其是“新版本解析成功前不改变旧版本”。主要风险在于发布事务和 RAGFlow 异步任务之间的一致性。

#### 风险点

1. `publish_job` 创建后 Worker 上传成功但数据库写绑定失败，会产生孤儿 RAG 文档。
2. RAGFlow 解析成功但质量检查失败，是否删除 RAG 文档、是否保留失败证据，需要定义。
3. 旧版本解绑与新版本激活的顺序必须保证检索无空窗或不越权。
4. 发布管理员与审核人是否允许同一人，需要按企业治理规则明确。
5. 解析成功不等于可回答，至少需要最小质量检查，例如 chunk 数、引用定位、有效文本比例。

#### 建议

- 发布采用状态机：`PENDING -> UPLOADED -> METADATA_SET -> PARSING -> EVALUATED -> ACTIVATED`；
- 每一步都记录外部操作回执；
- 所有 RAGFlow 文档创建必须有幂等键；
- 绑定表对 `version_id + engine_profile_version` 加唯一约束；
- 激活必须是数据库事务；
- Worker 可重放但不可重复创建派生资产。

### 5.3 更新与回滚流程

该部分设计较稳健。最大风险是“回滚重新建立 RAG 绑定”如果依赖旧 RAGFlow 文档仍在，会受到已删除或索引版本变化影响。

建议：

- 回滚优先复用仍有效的 binding；
- 如果 binding 不存在，重新从 FileBay 固定 commit 重建；
- 回滚前检查历史版本是否仍满足当前权限、有效期、分类和安全策略；
- 回滚不能绕过当前 K/R 策略。

### 5.4 暂停、下架与销毁

方案正确地区分了“检索阻断”和“物理销毁”。这是优点。

但仍需补充：

1. 下架成功的判定不能依赖 RAGFlow 删除成功；
2. 检索 API 必须以知识控制表状态为第一判定；
3. RAGFlow 删除失败时必须持续告警；
4. Dify 会话历史中已引用内容如何处理，需要策略；
5. 缓存、日志、向量索引、备份、导出文件都要进入销毁范围说明。

### 5.5 每日对账

每日对账设计是必要的，但对生产还不够。

建议增加：

- 高频风险对账：下架/删除后 1 分钟、5 分钟、30 分钟专项检查；
- RAGFlow orphan document 扫描；
- FileBay 存在但知识控制表无登记的正式路径扫描；
- Dify 应用绑定外部知识源范围检查；
- API Key 使用异常检测。

## 6. 安全设计评估

### 6.1 TLS 与凭据管理

方案对现状问题识别充分：`verify=False`、`CERT_NONE`、NoSNI、IP 回退、明文 PAT、管理员凭据等都被列为 M0 必改项。

评审判断：M0 必须是硬门禁，不应只是工作包。

未满足以下条件，不得进入真实数据 MVP：

- 生产环境禁止关闭证书校验；
- 禁止 IP 绕过主机名验证；
- 管理员凭据进入 Secrets Manager；
- 用户 PAT 不返回前端；
- API Key 支持轮换和撤销；
- 日志过滤 Authorization、Cookie、Token、密码和正文片段；
- 历史配置和文档完成秘密扫描。

### 6.2 权限控制

方案提出“检索前授权 + 返回后二次复核”，这是正确设计。原因是 RAGFlow/Dify 的数据集和 metadata 过滤不能替代企业权限系统。

需要补强：

1. 权限快照：发布时记录 ACL 上限；
2. 查询时使用当前用户权限与发布 ACL 上限取交集；
3. 已撤权用户必须立即无法检索；
4. 引用链接也必须二次鉴权；
5. FileBay Raw API 不得成为绕过知识权限的旁路。

### 6.3 文件安全与提示注入

方案列出了白名单、MIME、大小、压缩层级、病毒、宏、提示注入等方向，合理但还偏原则化。

建议 M1 明确以下验收项：

- OOXML 宏、ActiveX、外链、嵌入对象检测；
- PDF JavaScript、附件、超大图片检测；
- ZIP bomb / 解压炸弹防护；
- OCR 资源配额；
- 文档指令不得进入 system/developer prompt；
- RAG chunk 必须带来源边界；
- 工具调用与检索内容隔离。

## 7. 综合评估

### 7.1 最大三个优点

#### 优点一：权威系统分层清晰

方案没有把 RAGFlow 或 Dify 当成知识主库，而是明确 FileBay 负责文件物理副本，知识控制模块负责业务状态，RAGFlow 负责派生索引，Dify 负责应用编排。这是企业知识库能否长期治理的关键。

#### 优点二：双版本模型设计正确

将 Git commit/blob/LFS OID 与业务 version_id 分离，可以解决路径移动、文件重命名、版本回滚、生效期、替代关系等问题。

#### 优点三：对安全和生产风险有基本敬畏

方案已识别 TLS、Token、个人仓库与正式知识隔离、AI 写入边界、下架阻断、每日对账、Git 难销毁等关键问题，比一般“RAG 拼装方案”成熟。

### 7.2 三个致命缺点

#### 缺点一：MVP 范围仍然偏大，实际交付风险高

M1 同时覆盖领域模型、知识空间、数据源、版本、审核发布、RAGFlow、Dify、生命周期、审计、前端和任务中心。即便 5 人团队，8—12 周也偏紧，尤其还包含安全整改、契约测试、容量 PoC 和运维手册。

#### 缺点二：FileBay/Git/LFS 的容量与销毁边界仍是系统性风险

方案承认该风险，但如果业务方误以为“已下架 = 已销毁”“Git 可当企业网盘无限扩容”，后续会形成严重技术债和合规风险。

#### 缺点三：RAGFlow/Dify 权限一致性依赖外围补偿，容易被实现细节击穿

只要 Retrieval API、Dify 应用配置、RAGFlow 数据集、FileBay Raw API、引用链接中任一处绕过知识控制模块，就可能发生越权。该风险不是架构图能解决的，必须靠强制网关、统一鉴权、契约测试和安全测试保证。

## 8. 改进建议与替代方案

### 8.1 P0：立刻调整为投产门禁

| 建议 | 操作 |
|---|---|
| 将 M0 作为真实数据前置门禁 | TLS、凭据、日志、秘密扫描、前端不接触 PAT 必须全部通过。 |
| 定义脱敏包协议 | 上传到知识库的必须是客户端已脱敏产物，含策略版本、manifest、hash、授权证据。 |
| 冻结版本组合 | FileBay、Desktop API、RAGFlow、Dify、数据库、embedding/rerank 模型统一记录版本和镜像摘要。 |
| 建立容量红线 | 在 M1 编码前完成代表性数据 PoC。 |
| 增加安全旁路测试 | 验证 Dify、RAGFlow、FileBay Raw、引用链接都不能绕过权限。 |

### 8.2 P1：收窄 M1 范围

建议 M1 只做一个明确场景：

- 一个租户；
- 一个业务域；
- K0—K2，不开放 K3；
- 人工数据源；
- 单级审批；
- 单 RAGFlow dataset 或少量 dataset；
- 一个 Dify 应用；
- 只支持 PDF/DOCX/MD/TXT 中经过 PoC 的格式；
- 不承诺物理销毁；
- 不做自动连接器；
- 不做文件级 ACL。

### 8.3 P1：强化状态机与数据约束

必须落库约束：

- 同一 file_id 只能一个 ACTIVE；
- 已发布 version 不可修改物理绑定；
- `version_id + engine_profile_version` 唯一；
- `publish_job.idempotency_key` 唯一；
- `rag_document_id` 不能无对应 version；
- 状态切换必须带 actor、reason、trace_id；
- 下架后检索 API 立即拒绝。

### 8.4 P1：RAGFlow Adapter 合同化

RAGFlow Adapter 应交付：

1. API 版本固定；
2. OpenAPI/接口契约文档；
3. mock server；
4. 契约测试；
5. 幂等策略；
6. 超时、重试、退避；
7. orphan document 清理；
8. 元数据白名单；
9. 删除回执与对账。

### 8.5 P1：Dify 接入采用“外部知识检索”模式

建议不要让 Dify 直接管理企业知识库内容，而是：

```text
Dify App
  -> CheersAI Knowledge Retrieval API
      -> 权限计算
      -> RAGFlow retrieve
      -> 返回后二次复核
      -> 引用封装
      -> 审计
```

这样可以利用 Dify 的应用编排能力，同时保留 CheersAI 对权限、审计、引用和生命周期的控制权。

### 8.6 P2：准备替代架构

当出现以下条件时，应评估替代方案：

| 触发条件 | 替代方案 |
|---|---|
| 文件容量或销毁要求超过 Git/LFS 能力 | 对象存储作为正文主存，FileBay 只存索引和元数据。 |
| 强文控、多级审批、保全要求明显 | 引入 Mayan EDMS 或客户已有 DMS 作为来源系统。 |
| 企业已有网盘体系 | Nextcloud/Seafile/SharePoint/NAS 作为连接器来源，而非迁移所有文件。 |
| 多客户、多租户、高 SLA | 知识控制模块拆成独立服务。 |
| 多 RAG 引擎需求 | 定义 Retrieval Engine SPI，RAGFlow 只是首个实现。 |

## 9. 建议的修订版架构门禁

建议在方案中新增以下“不得进入下一阶段”的硬性门禁：

### M0 出口门禁

- TLS 和证书校验合格；
- 无前端明文 Token；
- 管理员凭据可轮换；
- 原件不离开本地；
- 现有 FileBay 功能回归通过；
- 代表性文件格式初测完成；
- 安全扫描无高危秘密泄露。

### M1 启动门禁

- 容量 PoC 数字冻结；
- RAGFlow API 契约测试通过；
- Dify External Knowledge API 调通；
- 数据模型 DDL 和状态机评审通过；
- 脱敏包协议评审通过；
- 权限旁路测试用例设计完成。

### M1 上线门禁

- 上传—审核—发布—检索—下架闭环通过；
- 新版本失败旧版本可用；
- 下架后立即拒绝检索；
- RAGFlow 删除失败可告警和重试；
- Dify 无法越权访问；
- FileBay Raw API 和引用链接无法绕过权限；
- 备份恢复能重建 RAG 绑定。

## 10. 最终结论

该方案具备进入 PoC/M0 的价值，且总体方向比“直接把文件丢给 RAGFlow/Dify”的方案成熟得多。它的核心优点是保留 FileBay 作为文件和版本权威，新增知识控制模块作为业务治理权威，并把 RAGFlow/Dify 限定为派生索引和应用编排组件。

但它目前仍是一份“技术实现路线方案”，不是可直接投产设计。真正的成败不在于是否能调通 RAGFlow API，而在于：

1. 原件是否永不离开本地；
2. FileBay/Git/LFS 的容量和销毁边界是否讲清楚；
3. 知识控制模块是否成为唯一权限和生命周期裁决点；
4. RAGFlow/Dify 是否永远不能绕过授权；
5. 任务、对账、审计和恢复是否能覆盖失败场景；
6. M1 范围是否足够小，避免预算和周期失控。

建议当前项目决策为：

> 通过方向性评审，允许进入 M0 安全硬化与容量 PoC；暂不允许进入真实企业数据的 M1 开发与投产，直到 M0 门禁、脱敏包协议、RAGFlow/Dify 契约测试和容量基线全部完成。
