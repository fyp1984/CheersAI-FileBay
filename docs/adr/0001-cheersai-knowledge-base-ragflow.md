# ADR-0001：以 FileBay 为知识治理主库、RAGFlow 为主选检索引擎

- 架构决策状态：已接受
- 生产放行状态：未放行；须先冻结并通过 PoC 验收计划
- 决策日期：2026-07-15
- 决策范围：CheersAI 知识库、CheersAI-FileBay、RAGFlow 集成
- 决策所有者：CheersAI 产品与技术团队
- 取代：无

## 1. 决策摘要

CheersAI 企业知识库采用以下分层架构：

1. CheersAI Desktop 负责读取本地原始文件并在客户端完成脱敏；未脱敏原件不得离开本地设备。
2. FileBay 作为远端脱敏文件、知识元数据、版本、权限、审核发布和审计记录的权威系统。
3. RAGFlow 作为主选的文档解析、切分、向量化、索引、混合检索、重排和引用返回引擎。
4. CheersAI Knowledge Gateway 负责统一认证、授权计算、RAGFlow 凭据托管、检索前权限过滤、检索结果二次校验和审计。
5. CheersAI 知识库界面作为业务用户、知识管理员和运维人员的统一入口，不向普通用户暴露 RAGFlow 管理界面或 API Key。

RAGFlow 是可替换的检索能力组件，不是原始文件主库、企业权限主库或最终审计系统。FileBay 与 RAGFlow 之间不形成双主数据关系；RAGFlow 中的文档、分块、向量和索引均视为可从 FileBay 已发布快照重建的派生资产。

首期不将 Dify 作为默认依赖。CheersAI 继续承担应用入口、模型调用和智能体编排职责；未来如需引入低代码工作流平台，必须另行提交 ADR。

## 2. 背景与问题

CheersAI-FileBay 当前基于 Gitea 二次改造，已经具备私有仓库、组织与团队、版本历史、Git LFS、受保护分支、Webhook、API 和基础访问控制能力，但面向知识库的以下能力尚未形成完整闭环：

- 知识空间、知识文档和发布快照等领域对象；
- 草稿、待审核、已发布、已失效、已下架和已归档的生命周期；
- 来源部门、归口责任人、生效日期、失效日期、密级、适用范围等治理元数据；
- 文档解析、切分、向量化、索引、检索和引用链路；
- 文件权限到检索权限的可靠传递；
- 检索任务状态、失败重试、删除传播、索引回退和全链路审计；
- 与 CheersAI 知识问答、知识助手和智能体的统一集成。

企业知识库实施方案要求将前台应用、知识治理和后台知识处理解耦。RAGFlow 在复杂文档解析、摄取流水线、数据集管理、元数据、检索和引用方面具备较完整的现成能力，适合作为主选检索引擎；但其开源版数据集权限以个人或团队共享为主，不能直接替代 CheersAI 所需的租户、部门、岗位、项目、密级和文档级权限模型。

输入的《企业人工智能知识库落地全生命周期详细实施方案 V1.1》MD 与 HTML 内容及源文件哈希不一致。本 ADR 对“FileBay、CheersAI 与 RAGFlow 的产品分工和主选方向”作出独立且优先的架构决策；实施方案中的组织、流程和验收细则在完成版本统一后再作为需求基线，不能反向覆盖本 ADR 的隐私和权限红线。

因此需要在保留 FileBay 现有架构资产的同时，为 CheersAI 建立清晰、可审计、可替换的知识库分层。

## 3. 决策驱动因素

本决策优先满足以下要求：

1. **本地优先隐私**：未脱敏原始文件永不离开本地设备。
2. **单一权威来源**：远端脱敏知识、版本、审批、权限和生命周期只有一个权威系统。
3. **权限不放大**：远端发布、索引和问答不得超过来源授权证据与正式审批共同确定的发布授权上限。
4. **来源可追溯**：每个回答引用必须能追溯到 FileBay 中的知识空间、文档、不可变修订和发布记录。
5. **发布可控制**：上传不等于发布，发布不等于永久有效；错误知识必须可立即阻断并可回退。
6. **检索质量**：支持复杂版式、表格、扫描件、混合检索、重排、元数据过滤和引用返回。
7. **引擎可替换**：未来更换 RAGFlow、嵌入模型、重排模型或索引引擎时，不推翻 FileBay 治理体系。
8. **最小侵入改造**：优先复用 Gitea 已有仓库、权限、版本、LFS、队列和 Webhook 能力。
9. **可运营与可审计**：摄取、检索、发布、下架、授权和人工复核均可关联统一追踪标识。
10. **可私有化交付**：支持内网部署、独立升级、备份恢复、容量规划和供应链治理。
11. **上游零侵入**：不得 Fork、修改或向 RAGFlow 核心代码注入企业业务逻辑；RAGFlow 的频繁迭代必须可由版本化适配器承接。

### 3.1 术语与不可突破约束

| 术语 | 定义 |
| --- | --- |
| 本地原件 | 用户选择的原始文件及其未脱敏临时副本、批注、嵌入对象和元数据，只能存在于本地原件区 |
| 本地 Sandbox | 客户端完成脱敏后保存可提交副本、脱敏清单和校验信息的本地目录，不等同于原件区 |
| 可提交脱敏包 | 通过客户端脱敏、格式检查和本地敏感信息检查，带内容哈希和脱敏策略版本的 Sandbox 产物 |
| 远端工作区 | FileBay 中保存用户显式提交的可提交脱敏包及治理数据的服务端空间 |
| 发布快照 | 绑定不可变修订、审批、ACL 上限、有效期和索引代次的候选或生效记录 |
| 同步阻断 | 状态变更提交成功前，Gateway 已拒绝新的检索、引用和下载；不以异步物理删除完成作为阻断条件 |
| 逻辑隔离 | 通过独立租户标识、数据集、账号、缓存命名空间、密钥和强制授权形成的隔离 |
| 物理隔离 | 通过独立 RAGFlow 实例及独立数据库、存储、缓存和密钥形成的隔离 |

任何服务端检查都只能对已经脱敏的候选包进行校验和阻断，不得以“服务端再次脱敏”为由接收未脱敏原件。脱敏标准、字段分类和文件类型处理规则必须在 PoC 开始前形成版本化规范。

## 4. 架构决策

### 4.1 组件职责

| 组件 | 主要职责 | 明确不承担的职责 |
| --- | --- | --- |
| CheersAI Desktop | 读取本地原件、客户端脱敏、写入本地 Sandbox、由用户显式发起上传或提交审核 | 不把原件或未脱敏内容发送到服务端，不直接完成正式发布 |
| FileBay | 保存远端脱敏文件、知识元数据、版本、ACL、审核发布、上下架和审计事件 | 不在首期自行实现完整 RAG 引擎 |
| Knowledge Gateway | 认证、授权、检索范围计算、凭据托管、调用 RAGFlow、结果复核、引用封装、审计 | 不保存未脱敏原件，不信任前端传入的权限范围 |
| RAGFlow Adapter / Indexer | 将已发布快照幂等同步到 RAGFlow，管理解析任务、映射、重试、删除和重建 | 不决定业务内容能否发布，不成为权限权威系统 |
| RAGFlow | 解析、OCR、切分、嵌入、索引、混合检索、重排、引用与检索观测 | 不直接面向普通用户，不保存权威审批和 ACL |
| CheersAI 知识库界面 | 搜索问答、引用查看、知识提交、审核治理、反馈纠错和运营统计 | 不在浏览器中保存 RAGFlow 服务凭据 |

### 4.2 数据权威与处理区

| 层级 | 权威数据 | 规则 |
| --- | --- | --- |
| 本地原件区 | 未脱敏原件和未脱敏临时数据 | 永不出端，不得被服务端 API、Git、LFS 或模型服务读取 |
| 本地 Sandbox | 可提交脱敏包、脱敏清单和本地校验结果 | 只有用户显式选择的可提交脱敏包能够上传 |
| FileBay | 经用户显式提交的脱敏文件、治理元数据、修订、ACL、审批和发布快照 | 是远端知识治理和引用回溯的唯一权威来源 |
| RAGFlow | 文档副本、解析结果、分块、向量、关键词索引和检索统计 | 全部是派生数据，必须能够从 FileBay 已发布快照重建 |

禁止以下模式：

- Desktop 将本地路径发送给服务端并要求服务端读取；
- 未脱敏文件上传到 FileBay、RAGFlow、模型服务或日志系统；
- FileBay 与 RAGFlow 都允许独立修改同一份正式知识；
- 用户绕过 Knowledge Gateway 直接调用 RAGFlow；
- 仅依赖前端隐藏、数据集名称或 RAGFlow 元数据过滤实现授权；
- 普通文件上传或 Git push 直接改变生产索引。

知识空间的外部写入入口只接受带脱敏清单、内容哈希和策略版本的知识提交。标记为知识空间的仓库必须关闭面向用户和普通令牌的通用 Git push、仓库内容写 API 和直接 LFS 上传；受控知识提交通过校验后，才由内部最小权限服务账号写入 Git/LFS 底层存储。未通过校验的载荷在客户端拒绝发送，服务端仅可拒绝或隔离已经声明为脱敏的候选包，不得保留疑似未脱敏内容作为候选。非知识空间仓库不在本 ADR 的知识摄取范围内。

每个修订必须保存来源授权证据：企业来源系统 ACL 快照、数据源归口审批、合法授权合同，或个人文件提交者对内容处置权的声明。知识提交人只能提出共享范围，正式发布范围由审批角色确定，并且不得超过来源授权证据允许的上限；任何扩大范围都必须补充新的授权证据并重新审批。FileBay 不以本地操作系统 ACL 作为可自动继承的企业授权结论。

### 4.3 FileBay 领域模型与现有能力复用

FileBay 保留 Git/Gitea 作为底层版本与存储基座，但对 CheersAI 用户提供知识库领域界面和 API，不暴露不必要的 Git 术语。

| 知识库概念 | FileBay 实现策略 |
| --- | --- |
| 知识空间 | 关联私有仓库和组织/团队权限的 `knowledge_space` |
| 知识文档 | 关联仓库路径或 LFS 对象的 `knowledge_document` |
| 不可变修订 | 文件内容哈希、Git commit SHA、脱敏策略版本和来源授权证据共同标识的 `knowledge_revision` |
| 审核发布 | 独立的 `knowledge_approval` 与 `knowledge_publication`，可复用 Pull Request、评审和保护分支能力 |
| 发布快照 | 明确绑定一个不可变修订和生效区间，不以可变分支头作为引用依据 |
| 权限 | 复用组织、团队和仓库权限，并通过 `knowledge_acl` 增加部门、岗位、项目、密级和用途约束 |
| 大文件 | 使用 Git LFS 或 FileBay 已配置的对象存储，实际部署必须验证容量与备份策略 |
| 变更事件 | 业务事务与 `knowledge_outbox` 同事务写入，再异步驱动索引任务 |
| 审计 | 使用追加式 `knowledge_audit_event`，记录主体、动作、对象、授权结果、版本和 `trace_id` |

首期至少新增以下逻辑实体，具体字段和迁移方案由后续技术设计确定：

- `knowledge_space`
- `knowledge_document`
- `knowledge_revision`
- `knowledge_acl`
- `knowledge_approval`
- `knowledge_publication`
- `knowledge_index_binding`
- `knowledge_index_job`
- `knowledge_outbox`
- `knowledge_audit_event`

### 4.4 知识生命周期

知识生命周期拆分为三个相互关联但不混用的状态维度：

| 维度 | 状态 |
| --- | --- |
| 治理状态 | 草稿、待审核、已驳回、已批准、已撤回 |
| 有效性状态 | 计划生效、现行有效、已失效、已下架、已归档 |
| 索引部署状态 | 未索引、排队中、索引中、待评测、可检索、索引失败、已取代、删除中、已删除 |

用户界面中的“已发布”是组合状态：治理状态为“已批准”、有效性状态为“现行有效”、索引部署状态为“可检索”，并且当前授权和发布指针均有效。仅完成审批或仅完成索引都不构成已发布。

状态约束如下：

- 草稿和待审核内容不得进入生产检索数据集。
- 候选发布快照必须绑定不可变修订、审批记录、适用范围、生效时间、ACL 上限快照和单调递增的 `publication_generation`。
- 同一知识主题在同一适用范围内只允许一个现行发布版本。
- 到期、替代、撤权或主动下架时，FileBay 必须先写入拒绝优先的废止墓碑并提升授权撤销代次；Knowledge Gateway 同步阻断召回、引用和下载后，才能提交状态变更。随后异步清理 RAGFlow 在线文档、分块、向量、缓存和临时副本。
- 重新上架必须产生新的发布记录并重新完成评测和审批，不得直接恢复旧索引状态。
- 归档内容保留 FileBay 版本和审计证据，但不参与在线检索。

### 4.5 摄取与索引链路

知识摄取采用异步、幂等、可重试的发布链路：

```text
用户显式提交脱敏文件
  -> FileBay 待审核区
  -> 格式、查毒、元数据、权限和内容审核
  -> 创建不可变候选发布快照
  -> 写入 knowledge_outbox
  -> RAGFlow Adapter 创建或更新文档
  -> 设置治理元数据
  -> 启动解析与索引
  -> 轮询或接收任务结果
  -> 完成离线评测
  -> 以比较并交换方式切换当前发布和索引指针
```

每个索引任务必须使用稳定的幂等键，至少包含：

```text
tenant_id + knowledge_space_id + publication_id + publication_generation + revision_hash + engine_profile_version
```

`knowledge_index_binding` 必须记录：

- FileBay 租户、知识空间、文档、修订和发布记录标识；
- RAGFlow 实例、数据集和文档标识；
- 解析器、切分策略、嵌入模型、重排模型和索引配置版本；
- 内容哈希、同步状态、失败原因、重试次数和最后成功时间；
- 当前索引版本和上一稳定索引版本；
- 规范化解析清单版本、每个分块的内容哈希和整份清单的 Merkle Root 或等效完整性摘要。

每个知识空间必须维护单调递增的发布代次和当前指针。所有创建、更新、切换和删除任务都携带代次；Worker 在执行写操作前后均校验代次和废止墓碑。旧代次、已撤销发布或删除墓碑之前产生的重试任务必须被拒绝，不能重新创建文档或回切旧索引。回退只能选择仍满足当前 ACL、有效期和废止状态的历史索引，不能仅以“曾经稳定”为依据。

RAGFlow Adapter 是逻辑边界。首期可以复用 FileBay 现有队列框架作为内部异步 Worker，但必须通过接口隔离 RAGFlow 特有的数据结构，保留未来拆分为独立服务或替换检索引擎的能力。

### 4.6 在线检索与回答链路

在线请求按以下顺序执行：

1. CheersAI 将已认证用户身份和请求发送至 Knowledge Gateway。
2. Gateway 从批准的统一身份源获取当前主体属性，从 FileBay 获取当前知识 ACL、授权撤销代次和发布状态，不信任前端提交的授权集合。
3. Gateway 先计算允许访问的数据集、文档和发布快照，再调用 RAGFlow 检索 API。
4. RAGFlow 元数据过滤仅作为查询约束和纵深防御，不作为唯一授权机制。
5. Gateway 对返回分块逐条回查 `knowledge_index_binding`、ACL、发布状态和有效期，并按版本化规范化算法校验返回内容哈希是否存在于 FileBay 保存的解析清单；不合规或哈希不匹配结果必须丢弃、失败关闭并记录安全事件。
6. 仅将通过授权和时效校验的脱敏片段发送给模型。
7. 回答引用统一映射为 FileBay 文档、修订、页码或段落锚点，不把 RAGFlow 内部对象地址作为最终业务引用。
8. 下载或预览原文时再次执行 FileBay 权限校验，并使用短期受控访问凭据。
9. 全链路记录统一 `trace_id`，关联授权决策、检索候选、引用、索引版本、模型版本、输出和用户反馈。

有效授权采用拒绝优先的交集规则：

```text
有效权限 = 当前已认证主体属性
         ∩ 当前 FileBay ACL
         ∩ 发布快照 ACL 上限
         ∩ 当前有效性和发布指针
```

任何显式拒绝、下架墓碑、过期状态或授权撤销代次不一致都覆盖允许结果。ACL 收窄和人员撤权立即生效；ACL 扩大必须重新审批并产生新的发布快照，不能通过修改当前 ACL 自动扩大既有发布范围。身份源或 FileBay 授权服务不可用、版本不一致或超时时，Gateway 必须失败关闭。授权缓存键必须包含租户、主体、ACL 策略版本、授权撤销代次和发布代次，并在撤权或下架时主动失效。

审计默认记录标识、哈希、策略版本、授权结论和必要指标，不默认复制完整查询、候选片段或模型输出。确需留存内容时必须执行字段级脱敏、加密、单独授权和保留期限控制；关键安全审计写入失败时，高风险知识请求必须失败关闭。

RAGFlow 不属于内容完整性的信任根。Indexer 在索引激活前必须从 RAGFlow 导出或读取规范化分块，生成包含分块标识、原文锚点、规范化内容哈希、图片或表格摘要、解析配置哈希的解析清单，并将清单及其完整性摘要保存到 FileBay。Gateway 在线校验返回分块，后台任务按发布快照执行全量对账；任何未知分块、内容哈希漂移或清单代次不一致都会隔离对应索引并阻断召回。候选 RAGFlow 版本若无法提供足以完成该校验的稳定内容和标识，不得用于受限知识生产环境。

### 4.7 租户与权限隔离

采用“强逻辑隔离为基线、按风险升级为物理隔离、元数据过滤补充、返回前二次校验”的策略：

- 不同租户不得共享 RAGFlow 数据集、服务账号或答案缓存。
- 个人知识库默认按用户隔离；企业知识库按租户、知识域和安全等级划分数据集。
- 三级受限知识、强监管客户、合同要求独占资源或共享实例无法证明隔离时，必须按租户部署独立 RAGFlow 实例；其他场景是否共享实例由风险评审批准。
- 不将所有企业文档放入单一数据集后仅依赖 `metadata_condition` 过滤。
- Gateway 的检索凭据和 Indexer 的写入/删除凭据必须使用不同服务账号、独立密钥和独立网络策略，统一存放于服务端密钥管理系统并支持轮换。若候选 RAGFlow 版本不能提供满足最小权限的凭据或补偿隔离，相关场景不得通过生产门禁。
- RAGFlow 管理界面仅向受控运维网络和最小化管理员开放。
- 401、403、过滤后空结果、跨租户标识和异常下载必须进入安全监控。

### 4.8 部署边界

FileBay 与 RAGFlow 独立部署、独立数据库、独立升级，不共享数据库表或直接访问对方内部存储。集成只通过版本化 API 和异步任务完成。

RAGFlow 的具体稳定版本、Elasticsearch 或 Infinity、对象存储、嵌入模型、重排模型和高可用拓扑不在本 ADR 中冻结。实施 PoC 必须：

- 选择正式稳定标签并固定容器镜像 digest；
- 禁止生产使用 `main`、`nightly` 或可移动标签；
- 记录软件物料清单、许可证、镜像来源和漏洞扫描结果；
- 验证升级、备份恢复、索引重建和上一稳定版本回退；
- 根据真实文档量、日增量、峰值并发和服务等级完成容量测算。

### 4.8.1 RAGFlow 上游兼容与扩展边界

RAGFlow 处于快速迭代阶段，因此 CheersAI 对它采用“**官方稳定版本 + 外置适配层**”策略，而不是深度定制策略。以下规则为架构红线：

1. 不 Fork RAGFlow，不修改其核心代码、数据库表、对象存储结构、内部索引或官方 Compose 主编排；部署仅使用官方发布版本和最小网络覆盖配置。
2. FileBay 只通过 RAGFlow 公开、版本化 HTTP API 集成；不得直连 RAGFlow 的 MySQL、Elasticsearch/Infinity、MinIO 或缓存。
3. 企业知识治理、细粒度权限、审批、生命周期、审计、Dify 授权和检索结果二次校验只能实现于 FileBay、Knowledge Gateway、RAGFlow Adapter 或独立服务中，不能写入 RAGFlow 插件或核心分支。
4. `services/knowledge/ragflow` 是唯一允许理解 RAGFlow 请求/响应细节的代码边界。新增引擎能力先扩展该适配器的内部契约；当适配器规模或独立发布需求增长时，将其拆分为独立的 `knowledge-indexer` 服务，而不是侵入 RAGFlow。
5. 每次升级必须固定官方标签、提交和镜像 digest，先运行适配器契约测试、脱敏样本解析测试、授权回归、索引重建和回退演练；通过后才允许切换生产版本。
6. 上游 API 不兼容时，优先在适配器中提供新旧版本兼容实现或短期双写/双读验证。若无法满足权限、引用或数据完整性门禁，停止升级或更换检索引擎，不以修改 RAGFlow 核心作为绕过手段。

当前内部试用固定使用官方 `infiniflow/ragflow` `v0.26.4`；该版本必须随官方稳定版本发布节奏定期评估，但“追随最新稳定版”不等于直接使用 `main`、`nightly` 或未经验证的可移动标签。

RAGFlow、解析器、嵌入、重排和生成模型只能调用经批准的私有化或受控模型服务。模型服务的区域、出站目的地、训练使用、请求日志和保留策略必须进入数据流评审；脱敏数据仍属于企业数据，不能因为已脱敏而发送到任意外部模型。

## 5. RAGFlow 选型门禁

“主选 RAGFlow”不等于无条件投产。PoC 只能使用脱敏或合成数据，并通过脱敏失败变体覆盖批注、嵌入对象、隐藏文本、OCR、表格、宏和元数据等代表性风险。PoC 开始前必须由业务、知识管理、技术、安全合规和运维共同签署《PoC 验收计划》，冻结候选版本、模型、配置、评测集、数值阈值、测量方法、证据格式、负责人和退出条件。

| 维度 | 最低门禁 |
| --- | --- |
| 隐私 | 网络检查确认未脱敏原件、未脱敏临时数据和原始本地绝对路径出网为 0；只允许用户显式选择的可提交脱敏包出网 |
| 权限 | 每个发布范围都有来源授权证据和审批上限；跨租户、跨部门、跨岗位、超出来源授权和已撤权访问成功数为 0 |
| 追溯 | 所有使用检索知识的回答必须给出至少一个有效引用或明确拒答；全部引用映射到 FileBay 不可变修订和发布记录的比例为 100% |
| 生命周期 | 草稿、待审核、已失效、已下架和已归档内容召回数为 0 |
| 完整性 | 未知分块、被篡改分块、错误锚点和解析清单代次不一致均被 Gateway 阻断；已激活索引全量对账通过率为 100% |
| 删除传播 | 在线不可召回时限、在线派生数据清除时限、备份自然过期和法定保留例外分别定义；恢复流程必须先重放删除墓碑，避免已删除内容复活 |
| 幂等与恢复 | 重复事件不生成重复正式文档；任务可重试，索引可从 FileBay 快照重建 |
| 解析质量 | PDF、DOCX、PPTX、XLSX、扫描件和表格按冻结样本集分别验收，不以综合平均掩盖单类失败 |
| 检索质量 | 召回、排序、引用、有据性和拒答达到业务批准的基线，指标定义和样本集可复现 |
| 性能 | 摄取吞吐、检索 P95、并发、资源占用满足批准的服务等级和容量预算 |
| 运维 | 完成监控、备份恢复、升级、回退、依赖故障、索引损坏和 FileBay 降级路径演练 |
| 供应链 | 无未接受的阻断级漏洞，依赖、镜像、许可证和模型来源可追溯 |

任一隐私、越权、引用追溯或回退门禁不通过时，RAGFlow 不得进入生产。项目可以整改后复测，或根据同一接口和评测集评估替代引擎。

解析测试必须覆盖恶意文档、提示注入、知识投毒、宏、压缩炸弹、超大文件和解析器资源耗尽；处理在隔离环境中执行，采用格式白名单、文件与页数限制、CPU/内存/时间配额、查毒和人工复核触发规则。权限质量测试还必须验证文档级过滤后的有效召回，防止无权候选挤占 Top-K 导致授权用户错误空结果。

## 6. 实施阶段

### P0：架构与 PoC

- 冻结首批 1 至 2 个知识场景和脱敏评测数据集；
- 确定知识元数据、状态机、ACL 和发布快照合同；
- 建立 RAGFlow 隔离验证环境并固定稳定版本；
- 完成解析、检索、权限、引用、删除、容量和恢复测试；
- 输出 PoC 报告、风险清单和投产/退出结论。

### P1：FileBay 知识治理与摄取闭环

- 实现知识空间、文档、修订、ACL、审批和发布模型；
- 实现追加式审计事件和事务 Outbox；
- 实现 RAGFlow Adapter、任务状态、幂等、重试、删除和重建；
- 实现待审核、发布、下架、失效和归档流程；
- 完成接口契约测试和网络数据泄漏检查。

### P2：CheersAI 检索与用户体验

- 实现 Knowledge Gateway 和服务端密钥托管；
- 实现授权检索、返回前复核、引用映射、拒答和审计；
- 实现用户知识空间、企业知识空间、治理台和任务状态界面；
- 实现反馈纠错、无答案问题和典型问题回放；
- 使用白名单用户完成灰度试运行。

### P3：生产化与持续运营

- 完成监控告警、容量、备份、恢复、灰度和回退；
- 建立模型、解析器、切分、索引和知识快照版本管理；
- 建立质量评测、过期下架、知识保鲜和月度复盘机制；
- 根据业务影响分析确认可用性、RTO、RPO 和演练频率；
- 评估高可用、独立租户实例和后续检索引擎适配需求。

## 7. 结果与影响

### 7.1 正面结果

- 复用 FileBay/Gitea 已有版本、权限、LFS、队列和 Webhook 能力，减少重复建设。
- 使用 RAGFlow 的现成解析和检索能力缩短知识库首期交付周期。
- 治理层和检索层解耦，避免知识元数据、审批、权限和审计被单一引擎绑定。
- 明确本地原件、远端脱敏主库和派生索引的权威边界，降低数据泄漏和双主冲突风险。
- 错误发布、权限撤销和引擎替换均具备可验证的回退或重建路径。

### 7.2 成本与负面结果

- 新增 Gateway、Adapter、映射、Outbox、审计和运维链路，系统复杂度上升。
- RAGFlow 自托管依赖数据库、对象存储、缓存和文档引擎，需要额外算力、存储、备份和值守资源。
- FileBay 权限与 RAGFlow 数据集之间需要持续同步和一致性校验。
- 文档解析、嵌入和索引升级可能触发全量重建，必须维护蓝绿索引和容量余量。
- 业务用户界面需要隐藏 Git 和 RAGFlow 的底层概念，增加产品化工作量。

### 7.3 风险与补偿控制

| 风险 | 补偿控制 |
| --- | --- |
| 权限映射错误造成越权 | 检索前授权、物理数据集隔离、返回前复核、权限矩阵测试、安全告警 |
| 未脱敏内容进入服务端 | 客户端脱敏、禁止服务端读取本地路径、网络载荷测试、敏感信息扫描 |
| RAGFlow API 或版本变化 | Adapter 隔离、契约测试、固定镜像 digest、灰度升级、双版本回退 |
| 双主或内容漂移 | FileBay 单一权威、禁止 RAGFlow 直接编辑正式知识、定期哈希核对 |
| 下架后派生副本残留 | 同步拒绝清单、异步删除传播、缓存失效、删除结果验证 |
| 检索质量不足 | 冻结评测集、分层指标、解析/召回/重排分别归因、保留替代引擎退出路径 |
| RAGFlow 依赖多、运维复杂 | 容量规划、监控、备份、恢复演练、依赖故障降级和明确 SLO |

## 8. 被否决或暂缓的方案

### 8.1 由 RAGFlow 完全替代 FileBay

**结论：否决。**

虽然 RAGFlow 提供数据集、文件、文档和版本相关能力，但它不是 CheersAI 本地脱敏、企业治理和细粒度权限的权威系统。完全替代会使文件治理、审批和权限绑定到检索产品，削弱引擎可替换性，并与 FileBay 的产品定位重复。

### 8.2 将 RAGFlow 代码直接合并进 FileBay/Gitea 单体

**结论：否决。**

两者技术栈、依赖、发布节奏和资源模型不同。直接合并会显著增加升级冲突和维护成本，也无法获得清晰的故障隔离。采用独立部署和版本化 API 集成。

### 8.3 首期默认采用 Dify + RAGFlow

**结论：暂缓。**

CheersAI 已承担应用入口、模型交互和智能体能力。首期引入 Dify 会增加身份、权限、数据流、部署和运维边界。只有在出现明确的低代码编排需求且收益超过复杂度时，才通过新 ADR 评估。

### 8.4 FileBay 自研完整解析和 RAG 引擎

**结论：否决首期实施。**

自研会扩大范围并延迟知识治理闭环。保留统一 Adapter 接口和评测资产，以便未来在特定合规或性能场景下替换部分能力。

### 8.5 所有文档放入单一 RAGFlow 数据集，仅靠元数据隔离

**结论：否决。**

元数据过滤是检索条件，不是充分的授权边界。采用租户和安全域的数据集隔离，并在 Gateway 中执行授权和返回前复核。

## 9. 回退与退出策略

如果 RAGFlow 在 PoC 或生产运行中无法满足隐私、权限、引用、性能、运维或许可门禁：

1. 停止新发布快照向 RAGFlow 同步，FileBay 继续保存脱敏文件和治理记录。
2. Knowledge Gateway 将受影响知识库降级为 FileBay 关键词搜索、只读引用浏览或人工服务。
3. 保留统一检索 Adapter、发布快照、评测集和映射合同，使用相同数据与指标验证替代引擎。
4. 替代引擎通过门禁后，从 FileBay 已发布快照全量重建索引。
5. 验证新索引和引用映射后切换引擎指针，再按数据保留策略删除 RAGFlow 派生数据和凭据。

该退出过程不迁移未脱敏原件，因为未脱敏原件从未进入 FileBay 或 RAGFlow。

## 12. 复审条件

出现以下任一情况时必须复审本 ADR：

- RAGFlow 主版本或许可证发生重大变化；
- RAGFlow 权限模型能够可靠覆盖 CheersAI 全部租户和文档级授权要求；
- FileBay 不再承担远端脱敏文件或知识治理职责；
- CheersAI 引入新的应用编排平台或统一检索中台；
- 法律、监管或客户合同改变数据驻留、脱敏、审计或模型调用要求；
- PoC 或生产指标连续不满足已批准门禁；
- 发生未脱敏内容出网、跨租户召回或无法追溯引用的重大事件。
